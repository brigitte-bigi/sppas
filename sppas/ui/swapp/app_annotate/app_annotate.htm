Modelling

Problem and scope

Description

SPPAS annotates: it takes the files of a person and writes, beside them, what it found in them — the words, the sounds, the syllables, what was said at the same time as something else. What it can find is not one thing but a score of them, each with its own languages, its own configuration and its own needs.

The application "Annotate" is what stands between a person and those annotations. It shows the annotations which can be performed, lets them be selected and configured, performs the selected ones on the files, says what came of each, and keeps what it said so that it can be read again. It annotates nothing itself.

The annotations are not independent of one another. The phonetization needs the text normalization, the alignment needs the phonetization. Every annotation declares what it requires; what is missing is a place where a person can see it. A score of annotations offered as a flat list is a list one gets lost in.

"Annotate" is the page "Annotate" of the desktop interface of SPPAS, brought to the web. A person who knows the one must find her way in the other: the same five steps, the same lists, the same report. What differs is how the files are given and how what was produced is reached, because a web page does not read the disk of the person who looks at it.

"Annotate" belongs to the SPPAS ecosystem and relies on its automatic annotations, which it never exposes. It is available both as a page of the SPPAS Dashboard and as an online application, addressing the same need in two contexts of use: within a working session on a local corpus, or as an occasional service.

Accessibility is treated here as a functional requirement rather than an added quality: what "Annotate" exposes — what an annotation does, whether it can be selected, how far the annotations have gone, how each of them went — is of no use if it is not perceivable.

Defining the needs

Problem statement and objectives

Performing automatic annotations raises a difficulty which is not technical: the user has to decide, before anything happens, which annotations to perform, in which language, with which configuration and into which file formats — among a score of annotations whose names say little to whoever did not write them. The decision is taken on a list, and the consequences are read afterwards, file by file, in a report.

The central problem addressed by "Annotate" is thus:

how to let a user perform, on a set of files, the automatic annotations she selected, in the language and with the configuration she fixed, and read what came of each of them, without requiring any knowledge of how an annotation works.

This problem is sharpened by the conditions of use. Annotating is a batch operation: several annotations are performed, one after another, on a set of files whose contents are not examined when the user decides. It is also a long operation, and nothing can be undone: what an annotation wrote is written. "Annotate" must therefore let decisions be taken once and applied to every file, show how far the annotations have gone while they are performed, and remain accountable for each annotation and each file.

The objectives follow:

  • to let the user choose the output file format of every kind of file which is produced;
  • to let the user fix the language of the annotations, and another one for a given annotation;
  • to let the user find her way among the annotations, know what each one does and what it requires, select the ones to perform, and configure them;
  • to perform every selected annotation at one go on the files the user delimited, and to show how far it has gone;
  • to report what happened, annotation by annotation and file by file, and to keep the reports so that they are read again, or deleted;
  • to give the user access to the files which were produced, in a manner adapted to the context of use;
  • to guarantee accessibility, of the interface and of the information it exposes;
  • to remain the page the users of the desktop interface know.

"Annotate" does not aim to say what an annotation does or how: that is established in the API of SPPAS, whose classes are read here and not modelled. It does not aim to select the files, which are given by the provision of files, nor to show and check the options of an annotation, which is the service of the options'. What is left is the annotations as a set: which can be performed, which are selected, what they are performed with, and what came of it.

Expressing the needs

Choosing the output file formats

An annotation does not write one kind of file: what is produced is annotations, and it may be a sound, an image or a video as well. The user chooses one extension for every kind of file which can be produced, among those SPPAS is able to write for that kind; a default one is already selected, so that nothing has to be chosen by whoever has no preference.

Fixing the language

Most annotations need language resources, and a corpus is usually in one language. The user fixes it once, and every annotation which has resources for that language takes it. An annotation which has none is left without a language, and the user gives it another one on its own line. When the selected annotations do not all have the same language, the page says so rather than showing one of them.

Finding, selecting and configuring the annotations

The annotations are shown in three lists, one per type: those which take one file on its own, those which take two files of one speaker, and those which take two files of two speakers. From the main page, the user sees at once which lists hold a selected annotation.

In a list, each annotation says what it does, and gives the way to the published work it rests on — or, where there is none yet, how far its development has gone. It says what it requires, and the list is arranged so that an annotation comes after the ones it requires. Every annotation is shown, including the ones which cannot be selected on that machine: they are disabled and not hidden, so that two users have the same page, and what differs between them is what is installed.

Selecting an annotation selects no other. The user configures an annotation before it is performed, and what she fixed is kept as long as she stays on the page.

Delimiting the set of files to annotate

The files to be annotated come from the working context, not from the tool: in a working session, they are the files currently selected in the workspace; in an occasional use, they are the files the user brings to the tool. The requirement is the same in both cases — the user delimits a set, "Annotate" operates on that set, and none of its files is altered. The two contexts differ only in their material constraints, an occasional use being bounded by what a service can reasonably receive.

Performing the annotations, and following them

One gesture performs every selected annotation on the delimited files. The user may ask, before it, for one file gathering everything which was annotated for each file, to open it in an annotation editor. While the annotations are performed, the page says which one is being performed and how far it has gone, and nothing else can be started: there is one performance at a time.

Reading the procedure outcome report

The annotations are a series of operations sharing the same decisions. Some succeed, some do not, for reasons belonging to one annotation or to one file. The report is written while the annotations are performed, line by line, each line carrying how what it is about went. It is therefore readable whatever happened, including when the performance stopped before its end. The user reads it when the annotations have been performed, and reads again the reports of the previous ones; she deletes the ones which are of no use any more.

Reaching the produced files

Annotations which produce files the user cannot find have annotated nothing. In a working session, the produced files join the workspace and remain available to the following operations. In an occasional use, they are handed back to the user. The requirement is that the outcome be reachable without the user having to know where the tool put it.

Accessibility

Everything above rests on information being exposed: descriptions, languages, states, progress, reports. Contrast, legibility, text alternatives to any graphical encoding — an annotation which is selected, a line of a report which is an error —, keyboard operation and consistent terminology between the interface and the concepts are conditions of the tool working at all. On a web page, what is being decided and the list of the reports do not always fit side by side: the user says whether she sees the one, the other, or both.

Conceptual level

Requirements

The previous sections state what users need and why; this section states what the system does to answer it, and what it manipulates in order to do so.

Two markers are used throughout. [API-OK] denotes what is achievable with the current SPPAS API. [API-EXT] denotes what requires an extension of that API. A requirement marked [API-EXT] is part of the model; it remains inactive until the API supports it.

Concepts manipulated by the application

The data dictionary of this application. Thirteen concepts, and the model below names no other.

D1. Annotation
One automatic annotation SPPAS is able to perform. What it declares of itself — its name, its description, its types, its languages, its options, its references, how far its development has gone, what it requires — is written in the API and read from there.
D2. Type
What an annotation takes: one file on its own, two files of one speaker, or two files of two speakers. An annotation has one type or several.
D3. Selected annotation
An annotation the user decided to perform.
D4. Language
The language an annotation is performed in, among those it has resources for, or none. An annotation which has no language resource has no language.
D5. Kind of output file
What an annotation produces: annotations, and possibly a sound, an image or a video. Each kind is written with one extension.
D6. Output extension
The extension chosen for one kind of output file, among those SPPAS is able to write for that kind.
D7. Configuration
The values given to the options of one annotation.
D8. Requirement
An annotation which has to have been performed before another one.
D9. Merge option
A decision of the user: whether one file gathering everything which was annotated is created for each annotated file.
D10. Batch
The set of files delimited by the user, whose contents are unknown at the time decisions are taken.
D11. Performance
Every selected annotation performed at one go on the batch, with the decisions taken when it was asked for.
D12. Progress
Which annotation is being performed, and how far it has gone. It exists while a performance goes, and nothing of it is kept.
D13. Procedure outcome report
What a performance wrote of itself, line by line, while it went. Each line carries how what it is about went: OK, ERROR, WARNING, INFO or IGNORED. It is a file, and it is kept until it is deleted.

The language of the page, and the language of an annotation

There are two places where a language is fixed, and the second one exists because of the first.

The language of the page is chosen in one list, which holds every language at least one annotation has resources for, and the entry ---, which is no language. It is --- when the page is asked for. Fixing it gives it to every annotation which has resources for it; an annotation which has resources, but none for that language, is left without a language. An annotation which has no language resource is not concerned. Fixing --- leaves every annotation which has resources without a language.

The language of one annotation is chosen on the line of that annotation, among its own languages and ---. It is where the user gives a language to an annotation the language of the page left without one, and it changes no other annotation.

The list of the page then shows what the selected annotations hold: their language when they all have the same, --- when none has one, and the entry MIX when they do not all have the same. That entry is in the list only as long as it is true.

What an annotation requires

Every annotation declares the ones it requires. The page shows it on the line of each annotation, and each list is arranged so that an annotation comes after the ones it requires [API-EXT]: what requires what is written in the declarations, and the annex states what reading it asks of the API.

What is shown is not what is done. Selecting an annotation selects no other: one annotation is performed, what it wrote is corrected by hand, and the next one is performed on the corrected version. Selecting what an annotation requires in its place would perform the whole chain on what was not corrected.

The order in which the selected annotations are performed is the API's, and this application neither chooses it nor changes it.

The reports

Each performance writes one report, under a name no report bore before. The reports which are kept are listed beside the five steps, and one of them at most is checked: checking one unchecks the other. The report of the performance which has just ended is added at the top of the list, and checked.

Three things are done with that list: the checked report is shown; the checked report is deleted; every report which is not checked is deleted. Showing is offered only when a report is checked and its file is still there.

A report which is shown begins with the name of its file. Its lines are shown as they were written, and the state each of them carries is shown as what it is.

Online, there is no list of reports. The report of a performance is written where the files the user sent stand, with everything which was produced: it is one of the produced files. It is shown when the annotations have been performed, as it is locally; it is downloaded on its own, and it is in the archive which brings every produced file back at once. No report of a previous performance is kept for a given user, so there is nothing to list, to check or to delete: online, the panel of the reports is collapsed.

Conceptual model

Annotate holds no data of its own but the reports. Everything else it manipulates belongs to one performance being decided, and is derived from a small number of user decisions. This section states who it exchanges with, which data exist, what produces them, and on which event each treatment runs.

Conceptual model of communication

Four actors border Annotate, and only one of them is a person. Three are neighbouring systems.

Rules of organisation

  • RO1 — The client holds no knowledge of the annotations. What an annotation is, which languages it has and what it requires were written in the page by the server; the client shows and sets what is there.
  • RO2 — The two contexts of execution are one organisation, and the two deployments are one implementation. What differs is who exposes the batch, and where the reports stand.
  • RO3 — The decisions are taken in any order. The five steps are numbered for the person to read; none of the first three is a precondition of another, and only the performance requires them.
  • RO4 — The batch is exposed by a neighbour and read. Annotate selects no file, in either context, and alters none [402].
  • RO5 — A performance is started by one request and runs on the server, in a thread; where it stands is read on the progress the API was given, and its results replace what was shown when it ends. The failure of one annotation never ends it [503].
  • RO6 — One performance at a time. While one goes, the page offers nothing which starts another, resets the page or asks for another batch, and the server refuses what would [032].
  • RO7 — Locally, the reports are those of the folder of the logs of SPPAS, and they are listed, shown and deleted. Online, the report is one of the produced files, no list exists, and the panel of the reports is collapsed [707].
  • RO8 — A decision is taken in the page and sent with the performance. Choosing an extension, fixing a language and selecting an annotation make no request, and replace nothing of what is read [1005]. Resetting and asking for another batch are of another kind: they take the batch back, which is the server's.
  • RO9 — What was decided is carried between two requests by what the page transmits. What the server holds between two requests is the performance which is going — its thread and its progress — and the manager of the provision of files.
  • RO10 — The order in which the selected annotations are performed is the API's. What this application works out from what the annotations require is the order they are shown in [307], [502].
  • RO11 — The options of an annotation are shown and checked by the service of the options. Annotate hands them over and takes the values back; how that is done, and where, is that service's to say.

RO6 is what the desktop interface does without saying it: its progress is a modal dialog, and nothing can be clicked under it. A web page has no modal progress, so the rule is written.

A performance is never half done, because nothing of it is undone

What an annotation writes, it writes as it goes, beside the files. There is no moment at which a performance is half made and has to be undone: an annotation which failed stops nothing, and the ones performed before it wrote what they wrote [503].

A performance which stops is not repaired. Nothing more is written and nothing more is said. The report was written line by line: it holds what was done until then, and it is read as any other [603].

The order is not this application's

The selected annotations are performed in the order of the API. An annotation which requires one which was not selected is performed all the same. What is read of the requirements is read for the person: to show them, and to arrange each list. C9, C15

One performance at a time

The thread which performs the annotations is what says a performance is going. While it is alive, a request which would start another one, reset the page or start over is refused, and the page, which shows the progress in place of the five steps, offers none of them. C13

  • The annotations module is the only one which reads what an annotation declares. Arranging a list is the one thing it adds, and it is given everything it needs: it is tested with nothing installed.
  • The performance module is the only one which has the API perform annotations, so it is the only one to read again the day that API changes.
  • The reports module is the only one which touches a report. It does not write one: the API does.
  • Provision is the only one which calls the provision of files on files. It is given the manager of that service by the response.
  • Decisions is the only one which knows what the page transmits. It holds no state of its own between two requests.
  • Presentation decides nothing. What it shows was decided before it was called, and the JavaScript it carries renders and nothing else.

The batch is provided, not constituted

Annotate does not select files. It receives a batch from its execution context and alters none of its files. In a local session, that context is the SPPAS workspace, or the files the person designates with the file chooser of the machine. In an online use, the batch results from files brought by the user to the service.

Annotate therefore depends on the provision of files, a service of swapp which has its own dossier, exactly as Convert does: a workspace holding the files to be treated and them only is handed, what is produced is added to it, and it is given back. The page of the desktop interface is given the workspace by its parent and sends it back when the annotations have been performed; this one asks the service, and gives back to the service.

Which files an annotation takes among those of the batch is not decided here: an annotation which takes two files finds them from the workspace and from what it declares.

Implementation model: MVC

  • Model: knows the annotations, performs T08, reads and deletes the reports, and is the only one which calls the provision of files on files. It is a façade over the automatic annotations of SPPAS.
  • Controller: identifies the task requested, checks its preconditions, chooses the treatment to run, calls the model, and prepares the data for display.
  • View: renders the state, collects the decisions, triggers the events. No business logic; JavaScript is rendering and interaction support only.

What receives a request is not the controller. The WhakerPy response handles the URL, receives the GET or POST and the events it carries, calls the controller once for that request, and bakes the returned tree — either a full page or an update payload.

Model

The façade AnnotateModel exposes the single interface the application expects and delegates to four specialised sub-models.

ModelAnnotations holds the knowledge of the annotations. It makes a sppasParam and reads its steps: for each annotation, its key, its name, its description, its types, its languages, its references, how far its development has gone and its options. It reads the kinds of output file, their extensions and their default one from sppasFiles. It gives the languages of the page, which are the languages of every annotation put together, and it arranges a list by what its annotations require.

ModelPerformance performs T08. It names the report, fills a sppasParam with what was decided, makes the progress, and starts a thread in which sppasAnnotationsManager performs the annotations, the merge option being given to it first. It holds the thread and the progress, and nothing else: it says whether a performance is going, and where it stands.

ModelReports lists the reports of the folder of the logs — the text files whose name holds report —, reads one, and deletes those it is named. Reading gives the lines as they were written, each with the state it carries: a line which starts a result bears one of OK, ERROR, WARNING, INFO and IGNORED, in the language of the interface, and that word is what the state is read from.

ModelProvision is the only class which calls the provision of files on files, as in Convert: files_for_app(), lock(), release(), produced(), address_of(), address_of_all(), and finished.

Controller

The controller is called once per request. It rebuilds the current state exclusively from the data transmitted to it. What carries that state is one object, AnnotateRecord: the view serialises it and the controller parses it back, and neither of them holds it between two requests.

Tasks:

  • start — transmitted: nothing. Preconditions: none. Triggers: T01. Produces: the page in its initial state [012].
  • perform — transmitted: the extensions, the selected annotations, the language of each, the values of the options, the merge option. Preconditions: at least one annotation selected; batch not empty; no performance going. Triggers: T08. Produces: the progress.
  • update — transmitted: nothing. Triggers: nothing. Produces: the percent, the header and the text of the progress, alone.
  • complete — transmitted: the decisions. Triggers: T09. Produces: the report, the container of the provision of files and, online, the addresses.
  • show — transmitted: the checked report, the decisions. Preconditions: a report is checked and can be read. Triggers: T10. Produces: the report. Locally.
  • delete_checked, delete_unchecked — transmitted: the checked report, the decisions. Triggers: T11. Produces: the list of the reports which are left. Locally.
  • restart — transmitted: the decisions. Preconditions: no performance going. Triggers: T12. Produces: the page without batch, the decisions as they were. The provision of files starts over.
  • reset — transmitted: nothing. Preconditions: no performance going. Triggers: T13. Produces: the page in its initial state. The provision of files starts over.

Nine tasks for thirteen treatments. T02 to T05 happen in the page and make no request RO8: what they decide is transmitted with perform. T06 is handed to the service of the options, and T07 is the provision of files'. update and complete are sent as the Setup sends them: event_name carries the first, and event_bake the second. The answer to update has a status of 202 until the hundred is reached.

A line of a report which states a result has one of five states: OK, ERROR, WARNING, INFO or IGNORED. They are the API's, and the line is what carries them. A line which states no result has no state.

The sequence, from the first request to the report

  1. The page is asked for. The annotations are read with what each declares, the kinds of output file with their extensions and, locally, the reports; all of it is written in the page, in its initial state [012].
  2. The batch is read from the provision of files. It is empty, and what is missing is said [403].
  3. The user chooses extensions and fixes the language of the page. Nothing is sent, and the choice of language of every annotation follows [202].
  4. She shows the list of a type, selects annotations, fixes the language of one of them, configures another, and comes back. The button of that type says a selected annotation is there [302].
  5. She designates her files in the container of the provision of files, and says they are ready.
  6. She asks for the annotations to be performed. Everything decided is sent at once, and the page is not reloaded; the preconditions are read on what was transmitted and on the batch.
  7. The report is named, the batch is locked, and the API performs the selected annotations, in its own order, in a thread. The page shows the progress and asks where the performance stands until the hundred is reached.
  8. The page asks for the results. The report is shown, with the name of its file; locally, it is at the top of the list of the reports, and checked.
  9. What was produced is reached through the provision of files: online, by a link to the report and a link to the archive of every produced file.
  10. She comes back to the five steps, and performs other annotations on the same batch, or asks for another batch, or resets the page.

Steps 3 to 5 happen in any order, and any of them may happen twice. The only thing which requires them is step 6.

The error policy

LevelWhat happensWhat is done
1What was asked cannot be done now: no annotation selected, an empty batch, a performance already goingNo treatment runs, and what is missing or what stands in the way is said [022]. It is not an error and nothing is raised
2One annotation is concerned: it failedNothing of this application's: the API writes it in the report, with the state of the line which says it, and goes on to the next

What is raised is caught by the response which answers the request, and by nothing below it. What an annotation writes about its own difficulties is not an error of this application: it is what that annotation said, and it is shown as such.

The contracts

How to read them

pre is what has to be true on the way in, and what the operation does not check; post is what the caller can count on without looking. The treatments state their preconditions for one treatment; these state them for one operation, and the two say the same thing at two levels.

What holds everywhere

  • What is absent gives back an empty thing — an empty list, no language, no report — and never nothing at all.
  • Nothing of what was decided is held between two requests. What is held is the performance which is going, and the manager of the provision of files. C24
  • Only ModelPerformance has the API perform annotations, and only ModelAnnotations reads what an annotation declares.
  • Only ModelReports touches a report, and it writes none.
  • Only ModelProvision calls the provision of files on files.
  • A view decides nothing: what it shows was decided before it was called.
  • What is raised is caught by the response which answers the request, and no class below it writes a catch. What an annotation says of its own difficulties is not raised: it is in the report.

Annex: Extension of the SPPAS API

One extension is required by this document, and it is required by [307] alone.

E1 — What an annotation requires, read [API-EXT]

What The identifier of the annotation which has to have been performed before, carried by the declaration of an annotation and read with the rest of it.
Why The field is already written in the declarations — the phonetization says it requires the text normalization, the alignment says it requires the phonetization, the time group analysis says it requires the syllabification — and what reads a declaration does not read it. It reads the identifier, the name, the description, the type, the interface to run, the references, the degree of development, the options and the resources, and it passes over that one field. [307] asks for a value which is written and never loaded.
Bound to What an annotation requires — Requirements. Requirement [307].
What it costs One field read where the others are read. Nothing of what exists changes, and an annotation which declares nothing there requires nothing, which is what most of them say already.
What it is not It says what has to have been performed before, and never what will be made of an annotation afterwards: what follows one is read on the others.
Note What is written there is not all sound. One declaration names a requirement which no annotation bears, and one writes a requirement with a mark in front of it which no other has. Both are read the day the field is read, and neither is settled here.

What the current API already provides

For contrast, and to bound the extension above, the following are available and require nothing [API-OK]:

  • the annotations and what each declares, the activation, the language and the options of each, the output extensions, the workspace and the name of the report: sppasParam;
  • performing the activated annotations, with a progress and the merge option: sppasAnnotationsManager;
  • the kinds of output file, their extensions and their default one: sppasFiles;
  • the types of annotation: annots.types;
  • a name for each report, which replaces no other: sppasLogFile.
