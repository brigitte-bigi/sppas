User manual

Overview

This page performs the automatic annotations of SPPAS on your files. You say into which formats the files are to be written, in which language, which annotations are to be performed and with which options, and on which files. SPPAS performs them, then says what came of each of your recordings. Each annotation writes what it produced into new files.

The four spaces of SPPAS are here as everywhere else -- the header, the menu along the left edge, the body in the middle, the footer at the bottom. The help of the Dashboard describes them, and the menu buttons do the same thing here.

The body holds three buttons above two panels: the six steps on the left, the reports on the right. The steps are numbered in the order you go through them. Three of them open a panel which takes the whole body -- the annotations of one type, the files, the report -- and the Back button, at the top of that panel, brings you back to the six steps. Each part is shown below as you see it on the page.

The two panels

Above the two panels, three buttons say which one is shown:

Left shows the six steps alone, Right the reports alone, and Both shows them side by side, as when the page opens. On a narrow window, one panel at a time is easier to read. This changes what you see, and nothing of what is done.

Reset takes the page back to what it was when it opened: your choices and the files you gave go together.

1. Choose the output file format(s)

The first step holds one list per kind of file the annotations write: annotated files, images, videos and sounds, in that order. Each list offers the extensions SPPAS can write that kind of file with; the usual one is chosen when the page opens. Every file of that kind an annotation writes takes the extension chosen here: choose .TextGrid in the first list, and the annotated files are written in the format of Praat.

2. Fix the language(s)

The second step offers the languages at least one annotation has resources for. The one you choose is given to every annotation which has resources for it, and the others are left as they are; --- means that no language is chosen.

Each annotation has its own choice of language as well, in its line (step 3). When the annotations you selected do not all have the same, this list says MIX.

3. Select and configure annotations

The third step has one button per type of annotation:

  • STANDALONE -- an annotation of one input file;
  • SPEAKER -- an annotation of two input files of the same speaker;
  • INTERACTION -- an annotation of two input files of two different speakers.

Each annotation is one line:

  • The switch before its name selects it. Click the switch or the name: both do the same thing.
  • Configure... opens its options, in a window of their own. What you apply there is kept for that annotation; when you leave without applying, its options stay what they were.
  • The drawings after the name lead to the articles which describe the annotation. Each one opens in a new tab of your browser, and this page stays where it is. The drawing of a sheet is a document, the other one a web page.
  • An annotation which has no article shows a bar instead: how far its development has gone.
  • The list after them chooses the language of that annotation, when it has resources for languages.
  • Then comes its description, followed in italics by what it requires: Required files, the kinds of file it reads -- audio, video, image, annotated file, measure file; Required annotation, the annotation whose results it reads.

An annotation which cannot be performed on your computer is shown all the same, and nothing of it can be set: its switch and its button do not answer. Its description begins with Not installed on this machine., and a line, in the color of the errors, says why -- for instance, a feature of SPPAS which has to be installed first.

Back, at the top of the panel, brings you back to the six steps. What you selected is kept, and the button of a type which holds a selected annotation no longer carries the mark.

    5. Perform the annotations

    Create -merge files, when it is checked, adds one file per recording: its name ends with -merge, and it gathers all the annotated files of that recording into one.

    Let's go! performs the annotations. It does not answer while no annotation is selected, and the page says so under it: No annotation is selected. When no file is selected, the page says No file is selected. and nothing is started.

    Developer manual

    Organization

    The application lives in sppas/ui/swapp/app_annotate/. It follows the MVC pattern shared by every application of the swapp package. What each class holds, and why, is the subject of the Modeling chapter; this section says where to look.

    • app_annotate.py -- swappAnnotateWebData, which answers which page it can bake: the page of the application, and the one of this document.
    • annotate_maker.py -- swappAnnotateResponseRecipe, the bakery of annotate.html: it holds the model, receives the events, answers the progress and the report alone, and decides whether the page is created again.
    • annotate_controller.py -- swappAnnotateController, built at every request: it reads the task a request carries, does it, and has the view build the page.
    • annotate_record.py -- swappAnnotateRecord, what a page transmits from one request to the next, the decisions held in a sppasParam, and what is to be shown.
    • annotate_model.py -- swappAnnotateModel, the only interface the controller reaches. It makes the four models below, and nothing else reaches them.
    • annotate_annotations.py -- swappModelAnnotations: the annotations and what each declares, whether it is installed and why not, the files and the annotations it requires, the kinds of output file and the languages.
    • annotate_run.py -- swappModelRun, which runs the annotations in the thread of sppasAnnotationsManager and follows them, and swappRootResult, what came of one root of the batch.
    • annotate_reports.py -- swappModelReports, the reports which are kept, and swappReportLine, one line of a report with the state it bears.
    • annotate_provision.py -- swappModelProvision, what the service of the files is asked for: the batch, and the address a produced file is reached at.
    • annotate_view.py and annotate_panels.py -- the HTML tree, and the panels it is made of.

    What the page is made of

    The panels

    The body is built by swappAnnotateView. The form of the run, annotate_form, is written first: every field and every button of the page is tied to it by its attribute form, whichever panel is written. What the record holds and the written panel does not show is carried in that form, hidden, and the next request rebuilds the record from all of it.

    By default, the toggle of the two panels is written, then swappActionAnnotatePanel -- the six steps and Reset -- and swappReportsPanel side by side. Otherwise, one panel takes the body, its way back and its title written by append_head(): swappAnnotationsPanel, the annotations of one type, with one dialog of options per annotation; swappFilesAnnotatePanel, the files; swappLogAnnotatePanel, the procedure outcome report, with the progress above it while a run goes, and swappResultsPanel under it once the run has ended.

    Two containers are not of this application. The one of the files is written by the service of the files, swappFilesManager, which the bakery creates with the identifier of the panel of the files: it is appended to that panel, altered in nothing, and answered alone as well. The one of the options of an annotation is written by the service of the options, swappOptionsManager, and placed in the dialog of that annotation.

    The events the page answers

    Every button of the page posts event_bake, and its value is the task:

    • annotate_annotations_ followed by a type -- the annotations of that type;
    • annotate_options_ followed by a key -- the options of that annotation, in its dialog;
    • annotate_files -- the panel of the files;
    • annotate_perform -- the run starts, when at least one annotation is selected and the batch is not empty; what is missing is said otherwise;
    • annotate_complete -- sent by the page once the run has ended: its report, and what came of every root;
    • annotate_show -- the report which is checked;
    • annotate_steps -- back to the six steps; after a run, the files start over and the decisions are kept;
    • annotate_reset -- the page as it was on arrival: the decisions and the files together;
    • annotate_delete_checked and annotate_delete_unchecked -- locally, the checked report is deleted, or every other one.

    One run at a time: while one goes, annotate_perform, annotate_reset and annotate_steps start nothing, and it is said. What the controller raises is caught by the bakery, and by nothing below: it is written in the log, and the page says that the annotations could not be performed.

    While a run goes, the page asks for event_name=annotate_update, every 200 ms on the local server and every second on a distant one. The bakery answers that one alone, with the percent, a header and a text, and a status of 202 until the hundred is reached: the page is not built again for a progress bar. event_name=annotate_report is answered alone as well, with the report of the run the page follows, as it is written. Any other event is offered to the service of the files.

    The model is held by the bakery, and the controller is built at every request: a run is longer than the request which started it.

    The client

    statics/js/annotate_manager.js, AnnotateManager, is given the interval by the view. It drives the three buttons which choose the panels; it opens the dialog of the errors, or the one of the information, when the server wrote in it; it offers the button of the sixth step when a report is checked, without any request. It asks for the options of an annotation, and for the run, without leaving the page: what the server answers is put in place by identifier, and the panel of the report takes the focus by its title when it arrives. It follows the run, asks for the report as it is written and each time it is unfolded, then for the results.

    statics/js/swapp_files.js is the client of the service of the files. It is started when the panel of the files is written, and only then: what is done in the container is sent without reloading the page.

    The stylesheets of the page are statics/css/main_swapp.css, the toggle group of Whakerexa, and statics/css/app_annotate.css, which holds what belongs to this page alone. The last one is loaded by this document as well: the parts of the page shown in the user manual are drawn by it.

    Modeling

    Problem and scope

    Description

    SPPAS annotates: it takes the files of a person and writes, beside them, what it found in them — the words, the sounds, the syllables, what was said at the same time as something else. What it can find is not one thing but a score of them, each with its own languages, its own configuration and its own needs.

    The application "Annotate" is what stands between a person and those annotations. It shows the annotations which can be performed, lets them be selected and configured, performs the selected ones on the files, says what came of each, and keeps what it said so that it can be read again. It annotates nothing itself.

    The annotations are not independent of one another. The phonetization needs the text normalization, the alignment needs the phonetization. Every annotation declares what it requires; what is missing is a place where a person can see it. A score of annotations offered as a flat list is a list one gets lost in.

    "Annotate" is the page "Annotate" of the desktop interface of SPPAS, brought to the web. A person who knows the one must find her way in the other: the same steps, the same lists, the same report. What differs is how the files are given and how what was produced is reached, because a web page does not read the disk of the person who looks at it.

    "Annotate" belongs to the SPPAS ecosystem and relies on its automatic annotations, which it never exposes. It is available both as a page of the SPPAS Dashboard and as an online application, addressing the same need in two contexts of use: within a working session on a local corpus, or as an occasional service.

    Accessibility is treated here as a functional requirement rather than an added quality: what "Annotate" exposes — what an annotation does, whether it can be selected, how far the annotations have gone, how each of them went — is of no use if it is not perceivable.

    Defining the needs

    Problem statement and objectives

    Running automatic annotations raises a difficulty which is not technical: the user has to decide, before anything happens, which annotations to perform, in which language, with which configuration and into which file formats — among a score of annotations whose names say little to whoever did not write them. The decision is taken on a list, and the consequences are read afterward, file by file, in a report.

    The central problem addressed by "Annotate" is thus:

    how to let a user perform, on a set of files, the automatic annotations she selected, in the language and with the configuration she fixed, and read what came of each of them, without requiring any knowledge of how an annotation works.

    This problem is sharpened by the conditions of use. Annotating is a batch operation: several annotations are performed, one after another, on a set of files whose contents are not examined when the user decides. It is also a long operation, and nothing can be undone: what an annotation wrote is written. "Annotate" must therefore let decisions be taken once and applied to every file, show how far the annotations have gone while they are performed, and remain accountable for each annotation and each file.

    The objectives follow:

    • to let the user choose the output file format of every kind of file which is produced;
    • to let the user fix the language of the annotations, and another one for a given annotation;
    • to let the user find her way among the annotations, know what each one does and what it requires, select the ones to perform, and configure them;
    • to perform every selected annotation at one go on the files the user delimited, and to show how far it has gone;
    • to report what happened, annotation by annotation and file by file, and to keep the reports so that they are read again, or deleted;
    • to give the user access to the files which were produced, in a manner adapted to the context of use;
    • to guarantee accessibility, of the interface and of the information it exposes;
    • to remain the page the users of the desktop interface know.

    "Annotate" does not aim to say what an annotation does or how: that is established in the API of SPPAS, whose classes are read here and not modeled. It does not aim to select the files, which are given by the provision of files, nor to show and check the options of an annotation, which is the service of the options'. What is left is the annotations as a set: which can be performed, which are selected, what they are performed with, and what came of it.

    Expressing the needs

    Choosing the output file formats

    An annotation does not write one kind of file: what is produced is annotations, and it may be a sound, an image or a video as well. The user chooses one extension for every kind of file which can be produced, among those SPPAS is able to write for that kind; a default one is already selected, so that nothing has to be chosen by whoever has no preference.

    Fixing the language

    Most annotations need language resources, and a corpus is usually in one language. The user fixes it once, and every annotation which has resources for that language takes it. An annotation which has none is left without a language, and the user gives it another one on its own line. When the selected annotations do not all have the same language, the page says so rather than showing one of them.

    Finding, selecting and configuring the annotations

    The annotations are shown in three lists, one per type: those which take one file on its own, those which take two files of one speaker, and those which take two files of two speakers. From the main page, the user sees at once which lists hold a selected annotation.

    In a list, each annotation says what it does, and gives the way to the published work it rests on — or, where there is none yet, how far its development has gone. It says what it requires. Every annotation is shown, including the ones which cannot be selected on that machine: they are disabled and not hidden, so that two users have the same page, and what differs between them is what is installed.

    Selecting an annotation selects no other. The user configures an annotation before it is performed, and what she fixed is kept as long as she stays on the page.

    Delimiting the set of files to annotate

    The files to be annotated come from the working context, not from the tool: in a working session, they are the files currently selected in the workspace; in an occasional use, they are the files the user brings to the tool. The requirement is the same in both cases — the user delimits a set, "Annotate" operates on that set, and none of its files is altered. The two contexts differ only in their material constraints, an occasional use being bounded by what a service can reasonably receive.

    Running the annotations, and following them

    One gesture performs every selected annotation on the delimited files. The user may ask, before it, for one file gathering everything which was annotated for each file, to open it in an annotation editor. While the annotations are performed, the page says which one is being performed and how far it has gone, and nothing else can be started: there is one run at a time.

    Reading the procedure outcome report

    The annotations are a series of operations sharing the same decisions. Some succeed, some do not, for reasons belonging to one annotation or to one file. The report is written while the annotations are performed, line by line, each line carrying how what it is about went. It is therefore readable whatever happened, including when the run stopped before its end. The user reads it when the annotations have been performed, and reads again the reports of the previous ones; she deletes the ones which are of no use any more.

    Reaching the produced files

    Annotations which produce files the user cannot find have annotated nothing. In a working session, the produced files join the workspace and remain available to the following operations. In an occasional use, they are handed back to the user. The requirement is that the outcome be reachable without the user having to know where the tool put it.

    Accessibility

    Everything above rests on information being exposed: descriptions, languages, states, progress, reports. Contrast, legibility, text alternatives to any graphical encoding — an annotation which is selected, a line of a report which is an error —, keyboard operation and consistent terminology between the interface and the concepts are conditions of the tool working at all. On a web page, what is being decided and the list of the reports do not always fit side by side: the user says whether she sees the one, the other, or both.

    Conceptual level

    Requirements

    The previous sections state what users need and why; this section states what the system does to answer it, and what it manipulates in order to do so.

    Concepts manipulated by the application

    The data dictionary of this application. Thirteen concepts, and the model below names no other.

    D1. Annotation
    One automatic annotation SPPAS is able to perform. What it declares of itself — its name, its description, its types, its languages, its options, its references, how far its development has gone, what it requires — is written in the API and read from there.
    D2. Type
    What an annotation takes: one file on its own, two files of one speaker, or two files of two speakers. An annotation has one type or several.
    D3. Selected annotation
    An annotation the user decided to perform.
    D4. Language
    The language an annotation is performed in, among those it has resources for, or none. An annotation which has no language resource has no language.
    D5. Kind of output file
    What an annotation produces: annotations, and possibly a sound, an image or a video. Each kind is written with one extension.
    D6. Output extension
    The extension chosen for one kind of output file, among those SPPAS is able to write for that kind.
    D7. Configuration
    The values given to the options of one annotation.
    D8. Requirement
    An annotation which has to have been performed before another one.
    D9. Merge option
    A decision of the user: whether one file gathering everything which was annotated is created for each annotated file.
    D10. Batch
    The set of files delimited by the user, whose contents are unknown at the time decisions are taken.
    D11. Run
    Every selected annotation performed at one go on the batch, with the decisions taken when it was asked for.
    D12. Progress
    Which annotation is being performed, and how far it has gone. It exists while a run goes, and nothing of it is kept.
    D13. Procedure outcome report
    What a run wrote of itself, line by line, while it went. Each line carries how what it is about went: OK, ERROR, WARNING, INFO or IGNORED. It is a file, and it is kept until it is deleted.

    The language of the page, and the language of an annotation

    There are two places where a language is fixed, and the second one exists because of the first.

    The language of the page is chosen in one list, which holds every language at least one annotation has resources for, and the entry ---, which is no language. It is --- when the page is asked for. Fixing it gives it to every annotation which has resources for it; an annotation which has resources, but none for that language, is left without a language. An annotation which has no language resource is not concerned. Fixing --- leaves every annotation which has resources without a language.

    The language of one annotation is chosen on the line of that annotation, among its own languages and ---. It is where the user gives a language to an annotation the language of the page left without one, and it changes no other annotation.

    The list of the page then shows what the selected annotations hold: their language when they all have the same, --- when none has one, and the entry MIX when they do not all have the same. That entry is in the list only as long as it is true.

    What an annotation requires

    Every annotation declares the ones it requires. The page shows it on the line of each annotation.

    What is shown is not what is done. Selecting an annotation selects no other: one annotation is performed, what it wrote is corrected by hand, and the next one is performed on the corrected version. Selecting what an annotation requires in its place would perform the whole chain on what was not corrected.

    The order in which the selected annotations are performed is the API's, and this application neither chooses it nor changes it.

    The reports

    Each run writes one report, under a name no report bore before. The reports which are kept are listed beside the six steps, and one of them at most is checked: checking one unchecks the other. The report of the run which has just ended is added at the top of the list, and checked.

    Three things are done with that list: the checked report is shown; the checked report is deleted; every report which is not checked is deleted. Showing is offered only when a report is checked and its file is still there.

    A report which is shown begins with the name of its file. Its lines are shown as they were written, and the state each of them carries is shown as what it is.

    Online, there is no list of reports. The report of a run is written where the files the user sent stand, with everything which was produced: it is one of the produced files. It is shown when the annotations have been performed, as it is locally; it is downloaded on its own, and it is in the archive which brings every produced file back at once. No report of a previous run is kept for a given user, so there is nothing to list, to check or to delete: online, the panel of the reports is collapsed.

    Conceptual model

    Annotate holds no data of its own but the reports. Everything else it manipulates belongs to one run being decided, and is derived from a small number of user decisions. This section states who it exchanges with, which data exist, what produces them, and on which event each treatment runs.

    Conceptual model of communication

    Four actors border Annotate, and only one of them is a person. Three are neighbouring systems.

    Actors
    • A1. The user — she chooses the output extensions, fixes the languages, selects and configures annotations, asks for them to be performed, follows them, reads the report, reaches what was produced, and manages the reports.
    • A2. The provider of files — it hands Annotate a workspace holding the files to be treated, possibly empty, in both contexts of execution, and it is told what Annotate takes, gives back and produced. It is the domain of the provision of files, and the batch is what it hands.
    • A3. The API of SPPAS — it says which annotations there are and what each declares, which extensions each kind of output file can be written with, it performs the selected annotations, says how far it has gone, writes the report, and names the report of each run.
    • A4. The service of the options — it shows the options of one annotation and gives back the values which were fixed.

    F15 carries a workspace, and not what an annotation reads. Which files an annotation takes among those of the batch is settled between the workspace and what that annotation declares. This application chooses no file, pairs no file and looks for none.

    Nothing is written into what an annotation declares. A language fixed on an annotation, an annotation selected, an option configured: all of it is held for the run being decided, and the declaration is what it was.

    What goes to A2 is said of the workspace made for Annotate, and never of the one of the person, which never leaves that domain [402].

    Navigation

    Annotate is a single page, and it is made of seven panels: the six steps, the reports, one list of annotations per type, the files, and the procedure outcome report. The page holds the panel which is under the eye, and the reports beside the six steps; it holds no other.

    Going from one panel to another is a request. The button which asks for a panel sends the fields of the page to the server; the server writes the panel which was asked for and the page puts it in place of the one it held. Nothing of what the user decided is lost, because the request carries every field of the page, and the panel which arrives is written from what it carried.

    What a decision implies is therefore computed by the server, in one place. The language of the page, once fixed, holds for every annotation which has resources for it: the list of a type says so when it is written. Which types hold a selected annotation, which language the selected annotations hold — the entry MIX included — and whether anything can be performed: the six steps say so when they are written. None of it is computed twice, and none of it is computed in the browser.

    From the six steps:

    • the button of a type asks for the list of the annotations of that type, and the button at the top of that list asks for the six steps;
    • the button of the fourth step asks for the files, and the button at the top of that panel asks for the six steps. The step itself says how many files were chosen; where a workspace is already there, it says what it holds and offers no way in. What a batch holds is unbounded, and a step which held it would be a step the five others are read around;
    • running the annotations puts the progress in place of the six steps, then the procedure outcome report, and the button at its top asks for the six steps;
    • showing the checked report asks for the procedure outcome report the same way.

    A panel which arrives takes the focus by its title. What was focused stood in the panel which is gone, and a focus which falls back to the top of the document says nothing about what happened. The title of the panel which arrives is where it is put, so that what is read aloud is the panel which was asked for.

    The six steps and the reports stand side by side. A group of three radio buttons — the six steps alone, both, the reports alone — says how much of each is shown: two panels side by side are unreadable on a narrow window. Both is what the page opens on locally; online, the reports are collapsed.

    Rules of organization

    • RO1 — The client holds no knowledge of the annotations. What an annotation is, which languages it has and what it requires were written in the page by the server; the client shows and sets what is there.
    • RO2 — The two contexts of execution are one organization, and the two deployments are one implementation. What differs is who exposes the batch, and where the reports stand.
    • RO3 — The decisions are taken in any order. The six steps are numbered for the person to read; none of the first three is a precondition of another, and only the run requires them.
    • RO4 — The batch is exposed by a neighbor and read. Annotate selects no file, in either context, and alters none [402].
    • RO5 — A run is started by one request and runs on the server, in a thread; where it stands is read on the progress the API was given, and its results replace what was shown when it ends. The failure of one annotation never ends it [503].
    • RO6 — One run at a time. While one goes, the page offers nothing which starts another, resets the page or asks for another batch, and the server refuses what would [032]. The way back is one of those: coming back to the six steps is asking for another batch, which a run going forbids. It is therefore offered and not available, as everything else which cannot answer is.
    • RO7 — Locally, the reports are those of the folder of the logs of SPPAS, and they are listed, shown and deleted. Online, the report is one of the produced files, no list exists, and the panel of the reports is collapsed [707].
    • RO8 — A decision is taken in the page and sent with the next request, which asks either for another panel or for the run. Choosing an extension, fixing a language and selecting an annotation make no request of their own, and replace nothing of what is read [1005]. Resetting and asking for another batch are of another kind: they take the batch back, which is the server's.
    • RO9 — What was decided is carried between two requests by what the page transmits. What the server holds between two requests is the run which is going — its thread and its progress — and the manager of the provision of files.
    • RO10 — The order in which the selected annotations are performed is the API's. What this application works out from what the annotations require is the order they are shown in [307], [502].
    • RO11 — The options of an annotation are shown and checked by the service of the options. Annotate hands them over and takes the values back; how that is done, and where, is that service's to say.

    RO6 is written because a page offers everything at once. A dialog which covers the page while a run goes would hold the rule by itself; a page has to hold it in what it offers, and the server in what it accepts.

    The batch is provided, not constituted

    Annotate does not select files. It receives a batch from its execution context and alters none of its files. In a local session, that context is the SPPAS workspace, or the files the person designates with the file chooser of the machine. In an online use, the batch results from files brought by the user to the service.

    Annotate therefore depends on the provision of files, a service of swapp which has its own dossier: a workspace holding the files to be treated and them only is handed, what is produced is added to it, and it is given back. Annotate asks the service for it and gives it back to the service: it is handed no workspace, and hands none to anybody else.

    Which files an annotation takes among those of the batch is not decided here: an annotation which takes two files finds them from the workspace and from what it declares.

    Implementation model: MVC

    • Model: knows the annotations, performs T08, reads and deletes the reports, and is the only one which calls the provision of files on files. It is a façade over the automatic annotations of SPPAS.
    • Controller: identifies the task requested, checks its preconditions, chooses the treatment to run, calls the model, and prepares the data for display.
    • View: renders the state, collects the decisions, triggers the events. No business logic; JavaScript is rendering and interaction support only.

    What receives a request is not the controller. The WhakerPy response handles the URL, receives the GET or POST and the events it carries, calls the controller once for that request, and bakes the returned tree — either a full page or an update payload.

    Model

    The façade AnnotateModel exposes the single interface the application expects and delegates to four specialized sub-models.

    ModelAnnotations holds the knowledge of the annotations. It makes a sppasParam and reads its steps: for each annotation, its key, its name, its description, its types, its languages, its references, how far its development has gone and its options. It reads the kinds of output file, their extensions and their default one from sppasFiles. It gives the languages of the page, which are the languages of every annotation put together.

    ModelRun performs T08. It names the report, fills a sppasParam with what was decided, makes the progress, and creates a sppasAnnotationsManager with them and the merge option: its thread performs the annotations. It holds that manager and the progress, and nothing else: it says whether a run is going, and where it stands. The first time it finds the run ended, it releases the batch, gives back what was produced, keeps as the results of that run what the API wrote under each root of the batch, and says it has finished. The results are those of the last run which ended, until another one starts.

    ModelReports lists the reports of the folder of the logs — the text files whose name holds report —, reads one, and deletes those it is named. Reading gives the lines as they were written, each with the state it carries: a line which starts a result bears one of OK, ERROR, WARNING, INFO and IGNORED, in the language of the interface, and that word is what the state is read from.

    ModelProvision is the only class which calls the provision of files on files: files_for_app(), lock(), release(), produced(), address_of(), address_of_all(), and finished.

    • annotations — transmitted: the decisions, and the type which is asked for. Preconditions: none. Triggers: T01. Produces: the panel of the annotations of that type.
    • files — transmitted: the decisions. Preconditions: none. Triggers: T07. Produces: the panel of the files, holding the container the provision of files writes.
    • steps — transmitted: the decisions. Preconditions: no run going. Triggers: T12 when a run has ended. Produces: the panel of the six steps.
    • show — transmitted: the checked report, the decisions. Preconditions: a report is checked and can be read. Triggers: T10. Produces: the report. Locally.
    • delete_checked, delete_unchecked — transmitted: the checked report, the decisions. Triggers: T11. Produces: the list of the reports which are left. Locally.
    • restart — transmitted: the decisions. Preconditions: no run going. Triggers: T12. Produces: the page without batch, the decisions as they were. The provision of files starts over.
    • reset — transmitted: nothing. Preconditions: no run going. Triggers: T13. Produces: the page in its initial state. The provision of files starts over.

A request which carries no event_bake carries no task of this application, and the response offers it to the provision of files. The decisions are carried by one field each, and they travel with every request whatever its task: annotate_ext_<kind>, one per kind of output file; annotate_lang, the language of the page; annotate_ann_<key>, one per selected annotation, of value True; annotate_lang_<key>, the language of one annotation; annotate_opt_<key>_<option>, the value of one option of one annotation; annotate_merge; and annotate_report, the report which is checked. The task annotations carries the type it asks for in its own value: annotate_annotations_STANDALONE, annotate_annotations_SPEAKER, annotate_annotations_INTERACTION. The task options carries the key of the annotation it configures in its own value, annotate_options_<key>, which is also the identifier of the dialog of that annotation. It is sent without leaving the page: when Configure is clicked, and with each form of the service of the options in that dialog, whose fields travel with the ones of the page. It is answered with the container of that service and with the values of the options of that annotation, which the page writes in its hidden fields.

    A run
    StateWhen

    A line of a report which states a result has one of five states: OK, ERROR, WARNING, INFO or IGNORED. They are the API's, and the line is what carries them. A line which states no result has no state.

    The sequence, from the first request to the report

    1. The page is asked for. The annotations are read with what each declares, the kinds of output file with their extensions and, locally, the reports; all of it is written in the page, in its initial state [012].
    2. The batch is read from the provision of files. It is empty, and what is missing is said [403].
    3. The user chooses extensions and fixes the language of the page. Nothing is sent, and the choice of language of every annotation follows [202].
    4. She shows the list of a type, selects annotations, fixes the language of one of them, configures another, and comes back. The button of that type says a selected annotation is there [302].
    5. She designates her files in the container of the provision of files, and says they are ready.
    6. She asks for the annotations to be performed. Everything decided is sent at once, and the page is not reloaded; the preconditions are read on what was transmitted and on the batch.
    7. The report is named, the batch is locked, and the API performs the selected annotations, in its own order, in a thread. The page shows the progress and asks where the run stands until the hundred is reached.
    8. The page asks for the results. The report is shown, with the name of its file; locally, it is at the top of the list of the reports, and checked.
    9. Under the report, the results: one line per root of the batch, its status and the files produced under it. Online, each of them is a link, and a link brings the archive of all of them, the report included.
    10. She comes back to the six steps, and performs other annotations on the same batch, or asks for another batch, or resets the page.

    Steps 3 to 5 happen in any order, and any of them may happen twice. The only thing which requires them is step 6.

    The error policy

    LevelWhat happensWhat is done
    1What was asked cannot be done now: no annotation selected, an empty batch, a run already goingNo treatment runs, and what is missing or what stands in the way is said [022]. It is not an error and nothing is raised
    2One annotation is concerned: it failedNothing of this application's: the API writes it in the report, with the state of the line which says it, and goes on to the next
    3A report cannot be read, or cannot be deletedIt is said in error_dialog, with the reason, and a report which cannot be read is said in the panel of the report as well; a report which cannot be deleted stays in the list, and the others are deleted all the same
    4Whoever runs the machine has to know: the annotations cannot be read, a run cannot be startedSaid where he reads it, the log of the server, and the person is told in error_dialog that the annotations could not be performed: the response catches what the controller raised, and has the controller say it, say_not_performed()

    What is raised is caught by the response which answers the request, and by nothing below it. What an annotation writes about its own difficulties is not an error of this application: it is what that annotation said, and it is shown as such.

    The contracts

    How to read them

    pre is what has to be true on the way in, and what the operation does not check; post is what the caller can count on without looking. The treatments state their preconditions for one treatment; these state them for one operation, and the two say the same thing at two levels.

    What holds everywhere

    • What is absent gives back an empty thing — an empty list, no language, no report — and never nothing at all.
    • Nothing of what was decided is held between two requests. What is held is the run which is going, and the manager of the provision of files. C24
    • Only ModelRun has the API perform annotations, and only ModelAnnotations reads what an annotation declares.
    • Only ModelReports touches a report, and it writes none.
    • Only ModelProvision calls the provision of files on files.
    • A view decides nothing: what it shows was decided before it was called.
    • What is raised is caught by the response which answers the request, and no class below it writes a catch. What an annotation says of its own difficulties is not raised: it is in the report.

    What no test covers, and where they stand

    • The controller. It is owed, and it is what will check that a language an annotation has not is not kept, and that a disabled annotation is never selected.
    • The JavaScript. That a button sends the fields of the page, that the panel the server wrote takes the place of the one which was there, and that the focus lands on its title, is checked in a browser and not here. What that panel holds is checked here, because the server writes it.
    • What an annotation does. It belongs to the API and is tested there; this application is answerable for what it handed over.
    • The two services, which have their own dossiers and their own tests. What is checked here is the tie.
    • The wording, and the WCAG rules, which are verified on the page and not on a fragment of it.

    Six of the thirty-eight need nothing at all, eleven need nothing but the API, seven need annotations written for the tests, five need a disk, four need the neighbouring domain, and five the view.

    They stand where the project puts its own: in tests/swapp/, which follows the shape of the sources.

    Annex: What the SPPAS API provides

    What this document rests on

    Everything this document asks of the API is available:

    • the annotations and what each declares, the activation, the language and the options of each, the output extensions, the workspace and the name of the report: sppasParam;
    • running the activated annotations, with a progress and the merge option: sppasAnnotationsManager. Created with the parameters, the progress and the merge option, it runs them in its own thread, and is_alive() says whether they are running; created with nothing, annotate() runs them in the thread of its caller. Once they have been run, get_out_files() gives every file they wrote, the merged ones included;
    • the class of an annotation, by the name its step declares, get_api(), among the classes the package imports: instantiated, it raises sppasEnableFeatureError when a feature it needs is not enabled, with the message which says which one;
    • the annotations an annotation requires, by their keys: sppasParam.get_required_annotations();
    • the types of file of the inputs of an annotation, read on its class, which is not instantiated: get_input_filetypes();
    • the kinds of output file, their extensions and their default one: sppasFiles;
    • the types of annotation: annots.types;
    • a name for each report, which replaces no other: sppasLogFile.
